# Canonical migration executor fixtures

`node scripts/verify-migration-executor.mjs` exercises Prisma 8 RC's actual PostgreSQL migration executor. It is separate from the SQL renderer checks: it creates fresh, uniquely named databases and invokes `prisma db migrate`, `migration log`, and `db verify` against them.

The runner requires all of these explicit safeguards and clones the isolated local `postgres` foundation database:

```sh
MIGRATION_EXECUTOR_ADMIN_URL='postgresql://<local-admin>@127.0.0.1:<port>/postgres' \
MIGRATION_EXECUTOR_ALLOWED_PORT='<the exact local port>' \
MIGRATION_EXECUTOR_CONFIRM=CREATE_LOCAL_FIXTURES \
node scripts/verify-migration-executor.mjs
```

It refuses non-loopback hosts, ports outside the local native/Supabase defaults (`55432`, `55434`, and `54322`), an unapproved local admin role, a connection URL with query parameters/fragments, a non-`postgres` maintenance database, or a missing confirmation value. New databases are named `learnly_activation_executor_*` (within PostgreSQL's 63-byte identifier limit), are never reused, and are left in place for review. The runner does not drop databases, alter existing Prisma markers, or mutate any remote target. Do not point it at production, staging, a shared development database, or a remote tunnel.

The source foundation is the disposable local Supabase-compatible PostgreSQL database on port 55434, running `pgvector/pgvector:pg17` (PostgreSQL 17.11, pgvector 0.8.7). Before cloning, the runner verifies the base has no Prisma marker or app `public.User` table, no Auth users, no Storage objects, and no other active connections. If the local Auth, REST, and Storage services are using the database, stop those services briefly while cloning, then restart them as soon as fixture creation is complete. The runner never applies app DDL to the base database. Its fixtures inherit the local Auth/Storage catalog foundation, then add only missing compatibility roles/functions and the fixture-local `extensions, public` search path. The fresh and wrong-origin routes drop vector with `RESTRICT` inside their own clones so the canonical pgvector edge installs it in `extensions`. The c7 route retains the foundation's installed `extensions.vector`; the canonical executor's pgvector postcheck recognizes it before the edge attempts creation, then records the verified extension marker and ledger entry. Its app state and sample legacy rows are synthetic, not a live or byte-for-byte clone of production. These fixtures do not exercise Auth or Storage HTTP behavior, object persistence, or service-role behavior.

The fresh route preview is anchored at `@empty` and explicitly targets current contract `f099e7f519b2f869ca1c2cbbff3f96852f44830005b5af5a15022f4b813ce52b`, beginning with the reviewed `20261010T0331_fresh_supabase_mvp_baseline`. It includes the pgvector extension edge and current app migrations. This explicit target matters: `migrations/app/refs/db.json` still points at the old d7 baseline and must not be treated as current state. The test checks executor-selected edges against the preview, app and extension markers, contract profile verification, migration ledger, and repeat-apply no-op. The c7 suffix fixture is a definitions-only synthetic database rebuilt from the immutable c7 snapshot via Prisma's `db update --to`; its local app marker is written by `db sign c7 --no-advance-ref` only after schema verification passes. The extension marker and ledger are established by the canonical executor's verified existing-extension path, never by `db sign`. The fixture preserves synthetic learner IDs/content through canonical migrations. Never add a hand-written row to `prisma_contract.marker` or the migration ledger. A separate wrong-origin test uses a marker produced by a real migration and asks Prisma for an unreachable historical contract; the rejection must leave schema and marker unchanged.

PostgreSQL `db migrate` is transactional across the pending spaces in one run in the installed Prisma 8 RC. The rollback fixture starts from a CLI-established c7 app origin and verified pgvector state, then relocates the fixture's extension to `public` to trigger the known app `extensions.vector` precondition failure. It checks that pending app schema and marker/ledger writes roll back while the starting markers and deliberately relocated extension remain. `db sign` is used only to establish the synthetic app origin after schema verification; never use it for pgvector. The fixture setup and failure cause are recorded in the JSON result so the evidence distinguishes executor atomicity from feature/service journeys.

The canonical CLI `db verify` remains a blocker on the migrated fixture: 74 schema findings, including 30 exact `public` policy paths and 44 Auth/Storage catalog findings against this local stack version. Sol independently compared the actual public catalog with the generated, schema-verified baseline and found all 90 manifest expressions and all 30 public policies identical. The CLI findings remain visible and are not waived. The retained c7 suffix, wrong-origin, preinstalled-vector, and late rollback evidence is split across the JSON reports named in `migration-runbook-c7-to-f099.md`; it is not one end-to-end passing suite. Do not substitute `--marker-only` for full schema verification. Current local service images are GoTrue `v2.187.0`, PostgREST `v14.5`, Storage API `v1.41.8`; this local PostgreSQL 17.11/pgvector 0.8.7 stack differs from the read-only production inventory (PostgreSQL 17.6/pgvector 0.8.2). Current production inventory and the historical c7 marker/profile are contextual inputs only. Local executor evidence does not authorize a hosted migration or flag change.
